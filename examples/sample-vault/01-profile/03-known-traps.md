# Known traps — 反覆咬人的陷阱

> 每一條都是**被咬過**才寫進來的，格式固定四段：症狀／根因／驗證方法／可貼上的修法。
> 「我覺得可能會有問題」不寫在這裡，寫進 [[open-questions]]。
> 條目有編號，其他頁用編號引用（例如「見 known-traps 第 3 條」），編號不重用。

## 1. 客戶試算表的空白欄不是 0

- **症狀**（2026-01-18 觀察）：週報算出來的工時比實際少，但腳本不報錯，數字看起來也合理。
- **根因**：客戶把「當天沒做」留空白，匯出 CSV 後是空字串；腳本把空字串轉成 0 再加總，
  於是「沒填」和「填了 0」變成同一件事，少掉的是「有做但忘了填」的那些。
- **驗證方法**：匯出後先數一次空字串欄位數，和非空欄位數一起印出來。兩個數字加起來
  不等於總列數，就是解析錯了。
- **修法**：空字串一律解析成 `unknown`，不是 0；總工時旁邊必須同時印出 `unknown` 的筆數。
  週報草稿裡有 `unknown` 就不能自動送出，要先問人。

## 2. 圖片檔名裡的全形空白，上線後 404

- **症狀**（2026-01-19 觀察）：本機預覽一切正常，部署到靜態主機後某幾張圖破圖，
  瀏覽器主控台顯示 404，但檔案明明在。
- **根因**：客戶提供的圖片檔名含全形空白與括號，本機檔案系統吃得下，
  上傳後被轉成百分號編碼，HTML 裡的路徑對不上。
- **驗證方法**：部署前對輸出資料夾跑一次檔名檢查，任何非 ASCII 檔名一律列出來。
- **修法**：素材進 repo 的第一步就改名成小寫 ASCII、連字號分隔，並在來源頁記下
  「原檔名 → 新檔名」的對照，這樣客戶問起還找得回去。

## 3. `--preview` 不是乾跑：它仍然會真的寄出

- **症狀**（2026-02-18 事故）：為了檢查版面，用 `--preview` 跑了一次週報產生器。
  終端機印出「預覽」字樣，信箱也沒有寄件備份——但兩個客戶當天都收到了那封未定稿的信。
- **根因**：那個旗標只跳過「寫入寄件紀錄」這一步，寄送本身照跑。
  它從來不是乾跑，是「少做一步的正式執行」，只是名字騙人。
- **驗證方法**：任何自稱乾跑的模式，都要能在**完全沒有網路憑證**的情況下跑完。
  跑不完，它就不是乾跑。
- **修法**：`--preview` 改名為 `--send-without-log` 並加上紅字警告；
  真正的唯讀模式另外做成 `--dry-run`，該模式下不載入任何憑證。
  寄送前一律停下來輸出草稿路徑，等人回一個字才繼續。見 [[proj-weekly-report-bot]] 的現行有效段。

## 4. 客戶寄來的「最終版」PDF 沒有版本號

- **症狀**（2026-02-04 觀察）：同一份需求簡報收到三次，檔名都叫「最終版」，
  內容有三處不同，而且不是每次都是後面那份比較新。
- **根因**：客戶那邊是多人各自存檔再寄，檔名只表達「寄的人認為這是最終版」。
- **驗證方法**：以 `02-raw/` 的收件日與寄件人為準，不看檔名。
  同一份來源收到第二次時，兩份都留，在來源卡上列出差異。
- **修法**：來源卡（見 [[02-raw/client-brief-2026-01/SOURCE]]）一定要寫收件日、寄件人與
  「這份和上一份差在哪」；彙編頁引用時指名是哪一次收到的那份。
