# client-feedback-triage（草稿，未晉升）

> **這是孵化區的草稿。** 只在一個客戶身上跑過兩次，第二次還改了分類定義。
> 可以照著做，但每一步的結果都要人看過。晉升門檻與現況見
> `03-wiki/skill-client-feedback-triage.md`。

## 什麼時候用

客戶一次給了五條以上的回饋，而且來源混雜（信件一部分、訊息一部分、會議裡講的一部分）。
少於五條、或全部來自同一封信時，直接處理比較快，不要為了用 skill 而用 skill。

## 什麼時候**不要**用

- 客戶只是問問題（「這個大概多少錢？」）——那是報價，不是回饋。
- 回饋只有一條而且很明確——直接做。
- 客戶在生氣——先打電話，分類等講完再說。

## 輸入

- 回饋原文。**逐條保留原話**，不要先改寫成自己的話再分類；
  改寫過的句子會把「客戶到底說了什麼」這個證據弄丟。
- 每一條的來源與日期（哪封信、哪次會議）。口頭的要標「口頭」。

## 步驟

1. **逐條編號並標來源。** 一條一行，附來源與日期。口頭的在行尾加 `（口頭）`。
2. **分四類**，一條只能進一類：
   - `現在就改`：在既有範圍內、工作量小於半天、不影響其他頁。
   - `要報價`：超出原範圍，或工作量大於半天。
   - `要客戶再確認`：需求本身不清楚，或與先前的文字需求衝突。
   - `不做`：明確超出範圍、或技術上會傷害其他需求。
3. **標 `（口頭）` 的一律不能進 `現在就改`。** 口頭回饋只是候選，
   要文字確認才算依據——這條沒有例外。
4. **`不做` 的每一條都要寫一句理由**，而且那句理由要能直接寄給客戶看。
   寫不出可以給客戶看的理由，就代表它不該是 `不做`。
5. **產出回信草稿**：四類各一段，`不做` 那段放最後並附理由。
6. **停下來給人看。** 這支 skill 到這裡結束，不寄信。

## 不能猜的事

- 一條回饋到底屬於哪個頁面／哪個需求——找不到對應就放 `要客戶再確認`，不要猜。
- 客戶的優先順序。除非客戶自己排過，否則不要替他排。

## 完成判準

- 每一條回饋都有編號、來源、日期、分類。
- 口頭來源的都沒有落在 `現在就改`。
- `不做` 的每一條都有一句可以直接給客戶看的理由。
- 回信草稿產出，且**沒有寄出**。

## 已知限制（為什麼還沒晉升）

- 四類的邊界只在一個客戶的語境下試過；`要報價` 和 `要客戶再確認` 很容易混。
- 第二個人跑過一次，四類裡有一類分得不一樣（細節見 `notes.md`）。
- 沒有處理過「客戶回饋和先前文字需求直接衝突」的情況。
