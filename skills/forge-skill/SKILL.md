# 建立有用的 skill

先讀你 vault 的 `ROUTING.md` 的 skill 路由與選用規則。
查看既有 skill、同名副本與相關 wiki 卡，先判斷更新既有能力是否足夠。

## 抽取門檻

有重用需求，而且能提供模型原本沒有的領域判準、可靠腳本或資產，才值得獨立成 skill。
一次性結果留在專案；只有通用提醒時，優先精簡既有規則。使用者明確指定的交付仍依其要求完成。

## 寫法

- 使用當前平台可用的 `skill-creator` 處理格式與驗證；同名工具有多份時依 ROUTING 選用，不串跑全部。
- 需要較深入的拆分判準時，讀 `writing-great-skills` 的參考正文；不假設跨平台都有同一個斜線命令。
- SKILL.md 保留用途、必要輸入、真正影響決策的規則、完成證據與停止條件；條件式細節移到 references。
- description 寫清何時使用，避免「任何工作都要觸發」。領域限制限定到其來源情境，不把單案失敗升成普遍禁令。
- 使用一致的語言與具體動詞；不強制技術說明套用行銷口吻或固定的修辭格式。
- 澄清與驗證依風險決定。已有授權的可逆工作直接完成；關鍵未知或尚未授權的外部動作才停在相應邊界。

## 落地

本體依 ROUTING 放在共用活檔或 active project repo。草稿轉正式時，先確認引用及差異，
保留版本／備份後移除重複全文；若有舊知識庫，只作歷史來源。
共用 skill 的平台入口與鏡像由來源清單及同步工具管理；新增名稱要登錄清單，不能只補 wiki 卡。
wiki 卡只保存目的、來源、狀態與必要的取代關係，不重抄整份操作流程。

## 驗證

檢查 frontmatter、引用與腳本行為。重要修訂用代表案例確認會正確觸發、遵守授權且產出可用結果；
格式檢查不代表語意或人類驗收。保留仍未驗證的項目，不宣稱跨平台實跑成功。
完成後同步鏡像、跑路由／來源檢查，再回報變更與驗證範圍。
