# verified-research — 按風險查證外部事實

> 寫給人看，也寫給 agent。一句話：**會影響決策的外部事實追到一手來源；高影響主張再交叉驗證，並記錄日期與適用範圍。**
> 蒸餾自一類反覆出現的查證失敗。

## 適用範圍

本流程用於會影響實作的外部事實。低風險且穩定的設定依一次可靠查證即可；
配額、價格、授權或高影響限制才要求兩條獨立路徑交叉驗證，且以當前一手資料為準。
下方情境只用來說明失敗模式，不可直接作為今天的限額。已驗證且條件未變的證據可重用，註明來源與時點。

## ⭐ 為什麼有這份（失敗模式，整套的核心）

設想一個情境：你在為某個自動化流程決定一個上限值。某個外部服務的用量上限，你查了**兩個二手來源**——一份第三方整理的說明、一篇工程部落格——兩邊講的數字一樣，於是你用「兩遍一致」定案，照那個數字寫死了流程與提示。

**結果是錯的。** 兩個二手來源**同時過時**：它們都抄自同一份舊版官方文件。追到官方的變更紀錄才發現，那個限制的**定義維度**已經改過，真正的瓶頸不是你查到的那個數字。呼叫邏輯、用量顯示、錯誤處理全都要重寫。

> 教訓一句話：**「兩個來源都這樣說」不是查證，是兩個來源剛好都沒更新。權威只有官方 changelog／變更紀錄／一手文件。**

## 步驟／做法（可照著做）

需正式查證的外部主張，依上述風險範圍使用下列步驟：

1. **find — 先廣撒網找出主張**
   用搜尋／既有 skill／二手文章把「候選答案」找出來。這步只負責**生出待驗證的主張**，不負責定案。把每個數字、限制、規則都列成一條條 claim。

2. **官方文件交叉核對（關鍵步，不只二手）**
   每條 claim 一定追到**一手官方源**：官方 API 文件、**變更紀錄／changelog／release notes**、官方 quota 或 pricing 頁、RFC、官方 repo。
   - **二手（部落格、問答網站、skill 內建知識、別人的 wrapper）只能當線索，不能當結論。**
   - 數字類、限制類、配額類**最容易過時**——一定去翻**官方的「變更紀錄」**，那裡才看得出「這個值最近改過沒」。一個現值不夠，要看它的**時間軸**。

3. **高影響主張交叉驗證**
   同一條高影響 claim 用兩條獨立路徑確認：當前官方文件加官方變更紀錄，或加授權範圍內的受控實測。低風險主張可只做一次可靠查證。
   - 反例：兩遍都是二手 → 等於沒查。
   - 正例：第一遍官方 quota 頁給現值，第二遍官方變更紀錄給時間軸——兩遍互相對齊、且都是官方。

4. **adversarial skeptic — 抽查每條來源真偽**
   收尾切換成「找碴」心態，逐條問：
   - 這個 URL 真的存在、真的是官方域名嗎？（不是別人轉述的官方）
   - 這頁**最後更新是什麼時候**？有沒有可能我看的是 cache／舊版／鏡像？
   - 這條規則有沒有**例外／分桶／條件**被我漏掉？（常見的：某類憑證不適用、某種測試模式另有上限、某些地區或方案自成一套）
   - 如果這條是錯的，**code 哪裡會炸**？爆炸半徑越大的，查越兇。

5. **落檔，每條附來源 + 標記信心**
   依交付需要放進既有文件或回覆，不為每次查詢新建檔案。每條附來源與觀察日期，並標：
   - ✅ = 已依該主張的風險完成所需查證；高影響項目需交叉驗證
   - 🟡 = 來自二手／skill，**待官方交叉核對**（誠實標出還沒追到官方的）
   把「由事實推導出的設計硬約束」也寫下來（例：查到的是每日上限 → 介面要顯示剩餘額度，而不是只在超額時報錯）。

## 判準（什麼算做對／做壞）

**做對：**
- 每條 claim 都能點到**官方一手 URL**，且我親眼看過它的「最後更新／版本」。
- 數字類都有**時間軸**（「這個值在上一版改過，這一版又改了一次」），不只一個孤立現值。
- ✅ 與 🟡 誠實分開——沒追到官方的不假裝查證過。
- 反推得出「這條錯了 code 哪會炸」，高爆炸半徑的查得最兇。

**做壞（出現任一即重查）：**
- 「兩個來源都這樣說」就定案，兩個其實都是二手。← 本 skill 的原罪。
- 引用了二手對官方的**轉述**，沒去看官方原文。
- 只抓到一個**現值**，沒查它最近有沒有被改過。
- 把 🟡（待核對）寫得像 ✅（已查證）。
- 例外／分桶／條件被整類吃掉（只看「主路徑」漏掉特例）。

## 可調的旋鈕

- **two-pass 的嚴格度**：低風險 config 一遍可靠查證即可；高影響配額、授權與合規欄位，使用當前一手文件及獨立變更紀錄／受控實測交叉驗證。
- **哪些算「官方一手」**：定義這個專案接受的權威源白名單（官方 docs 域名、官方 repo、RFC…），其餘一律降級成線索。
- **信心標記的門檻**：什麼程度才准標 ✅（例：必須附官方變更紀錄 URL 才算 ✅）。
- **skeptic 抽查的深度**：時間緊時抽查高風險條目；交付前對全清單跑一遍。
- **落檔粒度**：要不要連「由事實推導的設計約束」一起寫進去（建議要——這是事實能直接驅動 code 的地方）。

## 怎麼變特規（換人／換場景沿用）

固定核心 = **find → 官方一手交叉核對 → two-pass（含官方）→ adversarial 抽查 → 附源落檔**。可抽換的只有「**什麼是官方源**」：

- **換 API**（金流 / 模型供應商 / 雲端配額）：把「官方源」換成那家的 changelog／pricing／quota 頁，流程不動。
- **換領域**（法規／合規／學術數據）：官方源換成法條原文／主管機關公告／同儕審查原文，照樣「追一手 + 看版本時間 + skeptic 抽查」。
- **換人操作**：交付物固定是「每條附官方 URL + ✅/🟡 標記 + 推導出的硬約束」的清單，下一個人能依來源日期與條件判斷是否需要重查。
