# agent-handoff-pack — 讓對方的 agent 接得住

> 交接失敗有兩種：對方**看不懂**（只丟 code，要逆向工程才知道怎麼跑），或你**給太多**（把 live 憑證、含個資的資料庫塞進壓縮檔，一轉寄就外流）。這支 skill 同時擋住兩邊。

以下以一種常見的交接情境為例，步驟可直接照做。

## 步驟／做法

1. **寫進入點 `AGENTS.md`——交接包的第一句話是「先讀我」。** 內含四段，缺一不可：
   - **有哪些功能（誠實標「在哪跑」）**：做成表格，欄位是 `功能 | 在哪跑 | 狀態 | 入口檔`。關鍵是分清楚「在伺服器／雲端長期跑的服務」vs「要用 coding agent 開這個 repo 才跑得起來的 workflow」——交接最常被搞混的就是這條。狀態用 ✅已可用／⚠️未授權／⏭下一階段 三態，不要假裝全綠。
   - **怎麼讀這個 repo（地圖）**：逐一說明每個頂層資料夾是什麼（例如：能力定義、產生器、服務程式、資料快照），讓對方 agent 不用瞎逛。
   - **怎麼用／怎麼擴充（操作指南）**：給「產生一份新輸出」「操作執行環境」「重新部署」「開發一個新能力」各一條可照做的步驟串。
   - **機敏與紅線**：明寫「這個包裡沒有任何 live 憑證」，並指向憑證設定說明。
2. **放進全部 `skills/`**：每個能力一份 `.md`，寫給人也寫給 agent。對方 agent 照既有 skill 格式就能再加新能力——這是「能擴充」的本體。
3. **放進 code 與內容快照、抽掉 live state**：原始碼進包；資料用**快照檔**（可再生的匯出），但**含個資的資料庫留在原處，不進包**。
4. **寫憑證設定說明 ＋ `.env.example` 取代金鑰**：對每個要授權的能力，給一條「自己授權一次」的步驟（雲端 SDK 登入、OAuth 客戶端自建、平台 token 自行申請後 export）。`.env.example` 是欄位範本，真正的 `.env` 進 gitignore、不進包。
5. **打包前把紅線變成檢查**：確認忽略規則涵蓋 `.env`、金鑰目錄、token 檔與含個資的資料庫，然後對整包跑一次機敏掃描（你的 vault 的 `bin/scan_sensitive.py`，bootstrap 時已一併複製進去；沒有的話用 starter repo 的同一支），輸出必須是零 error 才封包。

## 判準（什麼算做對／做壞）

- **做對**：對方 agent 解壓 → 只讀 `AGENTS.md` 就知道「有什麼／在哪跑／怎麼用／怎麼擴充」；照憑證設定說明授權後功能真的能跑；包裡 `grep` 不到任何 live key／token／個資。
- **做對**：功能表誠實——未授權的標 ⚠️、沒接的標 ⏭，不灌水。
- **做壞**：把雲端登入憑證、OAuth token、計費型平台 key、含名單的資料庫塞進包裡。包會被轉寄＝外流；計費型的 key 別人一用就是你付錢；綁帳號或綁機器的憑證塞過去通常也過期無效。
- **做壞**：把「長期跑的服務」和「要開 agent 才跑得起來的流程」混為一談，讓對方以為點一下就會自動產出。
- **做壞**：只丟 code 不寫進入點，對方 agent 得逆向工程才知道怎麼跑。

## 可調的旋鈕

- **進入點檔名**：`AGENTS.md`（通用慣例）或 `HANDOFF-AGENTS.md`（當 repo 內已經有一份給自己用的 `AGENTS.md`，需要區分兩者時）。
- **快照 vs 不附**：哪些資料進包（可再生的內容快照）、哪些只留在原處（含個資的資料庫）——按敏感度切。
- **可給的門 vs 不可給的金鑰**：這是整支 skill 最需要拿捏的一條。**可給的門**＝只開到對方自己那份資源、可隨時撤銷、外流損失有界的存取（例如一組臨時憑據，用完即撤）；**不可給的金鑰**＝會計費、綁你的帳號或機器、撤銷成本高的憑證（雲端憑證、平台 API key、OAuth token）。前者可以寫進交接文件，後者一律走「對方自己授權一次」。
- **狀態標記粒度**：要不要把 ⚠️未授權 再細分（沒 client secret／沒 token／配額用罄）。
- **授權能力清單**：這個包要讓對方開通幾個能力（這個 repo 真正用到的那幾個外部服務），每個在憑證設定說明加一節。

## 怎麼變特規（換人／換場景沿用）

- **換接收方**：把進入點開頭的「給 X agent」與「先讀我，再讀 <對方的標準檔>」改成對方的慣例；功能表的「入口檔」對齊新 repo 結構。
- **換 repo 類型**：保留四段骨架（功能表、資料夾地圖、擴充指南、紅線），把內容換成該 repo 的；授權清單只列這個 repo 真正用到的服務，用不到的整段刪掉，不要留別的專案的殘影。
- **換交付形式**：壓縮檔改成 private repo 邀請時，金鑰紅線不變，只是把關的機制從「不進壓縮檔」換成 `.gitignore` 加上一次歷史掃描（git 歷史裡的舊金鑰一樣會外流）。

## 完成判準

包已封好，且你能同時指出：進入點的四段都在、機敏掃描零 error、以及「對方要自己授權的那幾件事」各有一條可照做的步驟。缺任一項就還沒完成。
