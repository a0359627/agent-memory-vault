# 跨專案盤點的證據與覆蓋

適用於已授權的全庫盤點（「看一下我最近在做什麼」「更新所有專案的狀態」「整理一下 skill」）。
不要因為走這個流程就部署、改權限或讀取無關的個人對話。

1. **從上一次盤點接著做。** 先讀最近一份 review、open questions、來源清單與 `git status`，記下 branch 與 worktree。
   歷史 review 保留原文，新結論寫進現行入口。
2. **覆蓋要看三個地方。** project card、近期 session 的工作目錄、所有相關的 worktree。
   主 checkout 沒有新 commit 不代表其他分支沒有工作；被 git 排除的 build／output 目錄用檔案時間掃，不能只看 `git status`。
   沒有卡片的活動另列「尚未定位／一次性／別人負責」，不要全算成自己的進行中專案。
3. **兩個欄位分開讀。** `status` 是這一頁的記憶生命週期，`subject_status` 才是專案或 skill 的狀態。
   重跑 `bin/scan-state.sh` 並寫明有沒有 fetch；它只證明磁碟活動與版控狀態，不證明服務在跑。
4. **指認「誰做的」要有證據。** 以 session 的中繼資料、事件格式、平台專屬標記與對得上的原始 session 為依據。
   一個平台的 session 目錄可能存著另一個平台的匯入紀錄；工作目錄、相同的使用者訊息、同一個 git author
   都不能單獨證明作者。證據不夠就記「來源平台未確認」。先列出這台機器上有哪些 agent 平台，一個都不要漏；不讀它們的憑證。
5. **skill 盤點是三件事。** 來源／入口／鏡像是否完整；本體是否還導向有效的流程；有沒有被使用與被接受的證據。
   平台自己觸發、使用者手動觸發、被當成一般文件讀取，三種分開算；同一個 session 的副本不能重複計數。
   不要用不完整的紀錄排出看似精確的排名，也不要因為低頻就刪 skill。
6. **新的偏好回原話核對。** 回到原始的使用者訊息確認日期與範圍。一次專案內的決定只收成有範圍的現行項或候選；
   較晚的更正可以取代較早的規格，但不能自動推廣到所有內容。原文含憑證時只保留去敏後的必要片段與來源定位，不整包對話入庫。
7. **只在有新證據時改。** 活檔或已核准的來源有新證據，才更新對應的卡片與鏡像；不手改 `08-skill-base/`。
   保留別人未完成的修改。涉及個人資料的內容要不要收，需要另外的授權；同步本身不構成許可。
8. **收尾把不知道的寫出來。** 列出覆蓋了幾個專案與截止時間、實際改了什麼、哪些執行狀態與人工接受沒有驗證、哪些歸屬未定。
   路由檢查零 error 不等於所有系統健康；不要為了看起來完整，把 unknown 填成完成。
