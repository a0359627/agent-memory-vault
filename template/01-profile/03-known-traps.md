# Known traps — 反覆咬人的跨切面陷阱

> 這一頁收的是**會再咬你一次**的東西，不是所有 bug。判準：同一個坑踩過兩次，或第一次就
> 花掉半天以上；而且它的症狀是「看起來成功、其實壞了」。
> 版本相關的條目屬條件性實測，使用前在當前環境核對，不據此宣稱新版本仍有或已修復同一問題。

## 條目格式

每條四段，缺一段就還不算一條 trap：

```
N. **一句話症狀（粗體，先講看得到的現象）**
   - **原因**：為什麼會這樣。寫機制，不寫「可能是設定問題」。
   - **驗證**：兩秒內能跑的斷言——什麼指令／什麼查詢，回傳什麼值代表中鏢。
   - **修法**：可以直接貼上去的那一行或那一段。
   - **適用條件**：哪個版本、哪個平台、哪種資料形狀才成立。條件消失時把它移到頁尾的歷史區。
   - **強制層級**：架構 | 型別／schema | lint／CI | 測試 | 文件 | 未強制
```

按症狀或工具分節；同一族的陷阱放一起，並在節首寫這一族的共同形狀。

**強制層級**回答的是「現在是什麼東西在擋這個錯」。只寫在這一頁的條目是「文件」那一層，也就是最弱的一層：
同一類錯被糾正第二次時，往上升一層（寫成測試、lint 或 schema），並在一個真實舊錯上證明新檢查會 fail。

## 九條通則（不綁工具，先讀這九條）

這九條不是條目，是判準。它們適用於你之後寫進來的每一條 trap。
前四條談系統行為，後五條談 agent 協作本身：檢查看的是什麼、授權動到哪裡、誰做了什麼、交接有沒有送到、
掃描擋得住什麼。

1. **「乾跑」必須是零副作用，否則不要叫乾跑。** 會寫入外部系統的東西——寫進下游、建立紀錄、
   觸發外部回呼——都不叫乾跑，叫「少做一步的正式執行」。要嘛做成真的唯讀，要嘛換個誠實的名字；
   因為叫它乾跑，人就會拿它去碰 production。
   *虛構例子*：某個「預覽模式」在算完結果後順手把來源標成「已處理」，於是預覽跑第二次就什麼都看不到了。

2. **多租戶化時，逐一稽核每個「不帶參數」的預設語意——它會靜默反轉。**
   單租戶時「不帶 X」＝「那唯一一個」；加了租戶維度之後，同一支端點變成「全部」，
   而下游服務**不會報錯**，只會開始吃到不屬於它的資料。同理還有「設定繼承全域預設」：
   對危險欄位（webhook 目的地、外部系統位址）要 fail-closed，方便性的繼承（逾時、模型名稱）留著沒關係。
   *虛構例子*：加了租戶欄之後，`GET /items` 從「這個租戶的項目」變成「所有租戶的項目」，
   下游報表安靜地多出別人的資料。

3. **回報要分層：API 200、成功 render 或測試通過只能證明對應層級。**
   （這條的出處是 `AGENT-RULES.md` 的回報分層那一行，不是某個工具的陷阱。）
   實作、測試、提交、合併、部署與人工接受是六件事；HTTP 202 只證明「請求被接受」，
   不證明「工作完成」，更不證明「人類接受」。
   *虛構例子*：批次任務回 202、佇列長度是 0，被當成「跑完了」——實際上是工作根本沒進佇列。

4. **外部系統的「建立時間」不是 immutable key。**
   凡是被排程、審核或發布流程碰過的時間戳都要當**可變欄位**處理：上游會改值的欄位，
   在 upsert 的更新清單裡漏掉一欄，那一欄就凍結在第一次寫入的值，而且全鏈路沒人報錯，
   症狀是下游安靜地全部算錯。
   *虛構例子*：上游會改寫的那個時間欄位沒被列進 upsert 的更新清單，於是本地 DB 永遠留著
   第一次寫入的值，以該欄位為準的任何時間區間統計從此長期偏差——沒有任何一層報錯。

5. **gate 要對「會被提交的東西」跑，不是對「磁碟上的東西」跑。**
   `.gitignore` 裡為了擋憑證檔而寫的字樣規則，會把檔名剛好含那個字的知識頁一起擋在 git 外。
   本機的檢查讀磁碟，所以全綠；任何一份 clone 裡，指向那一頁的連結都是壞的，而且沒有人收到通知。
   驗證：`git ls-files --others --ignored --exclude-standard -- 03-wiki 01-profile` 必須是空的
   （`./bin/check-routing.sh` 已把它當 error）。修法是改檔名，不是為單一頁面開 ignore 例外。
   *虛構例子*：一頁知識頁的檔名剛好含有被忽略的字樣；本機檢查一路全綠，遠端卻從來沒有這一頁。

6. **撤銷授權的範圍可能比你以為的大，而且症狀會延遲出現。**
   有些授權服務在撤銷一顆 token 時，撤掉的是「這個 client 對這個帳號」的整組授權。
   一支「只讀」的臨時腳本如果在收尾時撤銷自己的 token，共用同一個 client 的正式服務會一起失效；
   當下還沒過期的短效 token 會讓症狀晚一個週期才出現，因果就被時間切斷了。
   判準：臨時腳本用的 client 是不是正式服務那一把？收尾有沒有任何撤銷動作？任一為是就停手。
   修法：查真實資料另開一個 client 或用短效授權；會動到授權狀態的東西不叫唯讀（見第 1 條）。
   配套：fail-closed 的靜默失敗一定要配一條會主動打擾人的通道，log 裡的一行不算。
   *虛構例子*：臨時腳本跑完時一切正常；等短效 token 過期，正式服務才開始安靜地略過每一輪工作，而錯誤計數始終是 0。

7. **平台的目錄、檔名前綴與 git author 都不等於作者。**
   一個 agent 平台的 session 目錄裡可能放著另一個平台 session 的副本；幾個 agent 共用同一個 git 身分時，
   每個 commit 的 author 也都一樣。只看這些去回答「誰做了什麼」，會把整條線算到錯的 agent 頭上。
   盤點前先列出這台機器上所有的 agent 平台（正在跑的 app、家目錄下的 agent 資料夾、repo 的交接文件寫給誰），
   再拿使用者訊息跨平台比對：逐字相同就是副本。被 git 排除的產物用檔案時間掃，不能只看 `git status`。
   歸屬是推定的就寫「推定」。
   *虛構例子*：盤點報告把一項工作記在另一個 agent 名下，依據只是那份紀錄放在它的目錄裡；其實那是一份匯入的副本。

8. **交接文件寫好了，不等於交接送達。**
   交接寫給另一個平台的 agent，卻沒有任何訊息把它送進那個平台時，驗收關卡會靜默空轉；
   文件上的「等對方確認後再改狀態」又把狀態鎖住，沒有人負責，也不會報錯。
   驗證：交接之後，在對方平台的紀錄裡查不到這個 repo 的任何工作，就是沒有送達。
   修法：交接完成的定義是「對方收到的第一則訊息已包含交接檔路徑與清單本文」；
   `revisit_when` 一律帶日期，不鎖在另一方的動作上。
   *虛構例子*：交接檔列了一份確認清單，卻沒有任何一項留下執行痕跡——清單從頭到尾沒有出現在對方收到的任何訊息裡。

9. **secret 掃描擋不住個人資料。**
   secret 掃描認的是金鑰的形狀。把每個專案的 agent 記憶批次鏡像進 git 時，記憶裡若有不該進版控的個人資料，
   掃描一條都不會命中；「掃過了，沒有發現」是真的，也沒有用。
   修法：在 `bin/skill-sources.json` 的 `memory_exclusions` 按專案排除，排除發生在讀取內容之前；
   「這個先不要提交」的決定要落在下一個批次動作讀得到的地方，不能只活在一次對話裡。
   *虛構例子*：一句「這個資料夾先不要進版控」只說在對話裡；之後的批次同步讀不到那句話，照常把它收了進去。
